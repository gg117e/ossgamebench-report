## 抽出と評価を分ける

200 件は対象全体からの単純無作為抽出（非復元、種 20261112）。並びを project と番号で固定してから抽出する。
先頭 100 件で手引き・規則を調整し、残り 100 件で固定後の規則を評価する。audit を見て規則を直したら、その結果は最終評価として使わず、新しい未使用サンプルが必要。

従来案の「プロジェクトごとの上限」は、全 Issue に対する精度の標本を歪めるので主検証には使わない。
小規模プロジェクトや稀な種類の確認には別の補助サンプルを追加し、母集団の精度に単純合算しない。
100 件では少数カテゴリの再現率を安定して測れない。該当件数と混同行列を示し、少数なら分類をまとめるか探索的とする。

1. development のみを使って手引きと規則を調整し、版を固定する。
2. LLM は本文と手引きに基づき分類し、根拠の抜粋・確信度・実際のモデル識別情報を記入する。
3. 本人は `human_blind.jsonl` の 50 件を LLM の答えを開かずに分類する。未開封であることを本人が確認してから開始する。
4. 元の独立判定を保存した上で一致率と κ を算出し、不一致を別の欄で裁定する。LLM の自己確信度は正しさの証明にはしない。
5. audit の参照判定と規則の予測を照合する。LLM のみで判定した部分は人の正解とは呼ばない。

このセッションの分類者を Claude と記録しない。LLM は使用したサービス・モデル ID・日時・手引きの版を記録し、分からない識別情報は「未取得」とする。
既存計画にあるモデル名を今回の作業へ転記しない。現時点ではどちらの分類者の判定も入っていない。

## テストパスと RQ3 はデータ配置後

テストパス 100 陽性・100 陰性の案は、まず関連する修正で変更された `(project, path)` の母集団と抽出層の件数を保存してから実装する。
陽性・陰性を同数抽出した場合、層ごとの精度と全体の精度を区別する。母集団の適合率・再現率を出すには、各層の抽出確率で重みを戻す。
パスだけで迷うものは diff を確認し、不明を非テストへ置換しない。

RQ3 は実行テストの変更、fixture だけの変更、テスト基盤だけの変更を分け、各例で入力・操作・オラクルを抽出する。
サンプルはバグ Issue と PR の多対多対応を記録し、同一 PR の重複例を識別する。
