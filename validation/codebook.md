# バグ・再現情報・テスト変更の判定手引き

版：**v1-2026-11-13**（draft-2026-11-12 を development 100 件で試した後、1b 節「Issue の用途」と 3 節の diff の向きの注意を追加して固定）。
audit・本人の 50 件はこの版で判定する。版を変えた場合は、変更点と再判定の対象を記録する。
参照する既存分類と今回の変更点は [調査メモ](../results/research_review_2026-11-12.md) に記録した。

## 共通原則

- バグの種類と再現情報は、収録された Issue のタイトルと本文だけで判断する。コメント、PR、現在の GitHub ページを読んで補完しない。
  PR や diff を用いる別の調査では出典を明記する。
- 「確認できない」と「ない」を分ける。各 yes 判定に短い根拠の抜粋を残す。不明は unknown とする。
- 収録本文が投稿時点の原文とは限らない。編集履歴がないので「最初から添付されていた」とは書かない。
- まず `is_actual_bug` = yes / no / unknown を付ける。ラベルで選ばれていても、機能要求や質問である場合は no。
  母集団から勝手に消さず、選定規則の誤りとして記録する。主分類は unknown として評価対象の扱いを明示する。
- confidence は high / medium / low。rationale に理由を記入し、根拠が弱い断定を high にしない。
- LLM の回答は人の正解と区別し、独立判定の元回答を裁定で上書きしない。

## 1. 主な症状（primary_category）

症状への分類であり、コードの原因や開発者の役割の推定ではない。以下は既存体系を参考にした**本研究独自の操作的分類**。
根本原因が分からなくても、報告された実際の挙動から分類する。

| 値 | 含めるもの | 境界 |
|---|---|---|
| `crash_hang` | 異常終了、実行を継続できない例外、アプリ全体の停止 | ログに過去の exception があるだけなら該当しない。遅いだけは performance |
| `visual` | ワールドの描画、影、テクスチャ、アニメーション、カメラの不正表示 | メニュー・HUD の問題は ui |
| `audio` | 音が出ない、誤った音、再生時間や同期の異常 | 音声ファイルが原因という推測だけでは分類しない |
| `ui` | メニュー、入力欄、HUD、文字、ツールチップの表示・操作の異常 | ゲーム内の移動操作が効かない場合は gameplay |
| `gameplay` | 状態遷移、ルール、AI、衝突、移動、報酬等の異常 | ゲーム本体の症状が書かれている場合。エンジン API の一般的誤動作は tooling_other |
| `network` | 接続できない、切断、プレイヤー間の状態不一致 | マルチプレイで発生するだけでは network にしない |
| `save_load` | 保存できない、読み込めない、永続化した状態の欠落・破損 | 一般的なリソースの load やゲーム起動は自動的に含めない |
| `performance` | FPS 低下、処理遅延、メモリ増大等 | 回復しない完全停止は crash_hang |
| `tooling_other` | ビルド、エディタ、インポート、API 等の異常や、上記以外の明確な不具合 | 不明なものを押し込まない。ゲームとツールの区別はプロジェクト単位でも別記録 |
| `unknown` | 情報不足、互いに独立した複数バグで主症状を決められないもの | 不確かさを隠すため任意のカテゴリにしない |

**主症状の選び方**：タイトルと本文の中心となる実際の期待違反を選ぶ。原因の推測語やログ中の語の多さでは選ばない。
例（すべて説明用の架空例。実データの観察ではない）：

- 「セーブを読むと必ずアプリが落ちる」→ crash_hang、secondary_contexts に save_load。
- 「マルチプレイ中に影がちらつく」→ visual、secondary_contexts に network。同期不一致とは断定しない。
- 「セーブを読んだら持ち物が消えた」→ save_load。
- 「メニューの音量ボタンが押せない」→ ui、secondary_contexts に audio。

secondary_contexts は `save_load`, `network`, `audio`, `asset`, `ui`, `tooling` 等を複数選択可能とする。
二次タグは排他的カテゴリの割合に混ぜず、合計が 100% にならないことを明記する。
手引きの試行後に主分類を変更したら、対応表と再判定対象を記録する。

## 1b. Issue の用途（issue_domain）

プロジェクトがゲーム本体でも、Issue がプレイ中の不具合とは限らない。報告された不具合が**どこで起きるか**を 1 つ選ぶ。

| 値 | 含めるもの | 境界 |
|---|---|---|
| `player_runtime` | プレイヤーが遊ぶ実行中のゲーム（サーバー、Web 版、ゲーム内のメニューを含む） | 迷ったら本文に書かれた操作の場面で決める |
| `editor_tooling` | マップ・MOD エディタ、開発用ツール、テスト環境、デバッグ機能 | 製品に同梱されていてもプレイには使わない機能はこちら |
| `build_distribution` | ビルド、インストール、パッケージ、起動前の環境・依存関係 | 起動後のクラッシュは player_runtime |
| `project_meta` | 文書、リポジトリ設定、CI、Issue テンプレートなど | |
| `unknown` | 本文から判断できない | |

主分析（ゲーム本体のバグ）は player_runtime を中心にし、ほかは件数を示して感度分析に使う。

## 2. 報告の再現情報

`image`, `video`, `save_data`, `log_trace`, `steps` は、それぞれ yes / no / unknown。
外部の添付をダウンロードして内容を確認する作業とは分け、ここでは本文中にある具体的な情報・リンクの存在を測る。
unknown は分母・件数を別に示し、no へ自動置換しない。

| 項目 | yes | no / unknown の例 |
|---|---|---|
| image | 不具合に関係する画像の Markdown・HTML 埋込や明示的な画像リンク | プロジェクトのバッジやロゴは no。種類が不明の user-attachments URL は unknown |
| video | 不具合の挙動を示す動画への具体的なリンク・埋込 | 「動画を添付してください」は no。一般の紹介動画は no。GIF の静止/動画が不明なら video は unknown |
| save_data | 再現用セーブへの添付リンクやアーカイブのリンクがあり、本文からセーブを含むと分かる | 「セーブできない」は no。save.zip との言及のみでリンクなしは no。中身不明の zip は unknown |
| log_trace | 実際のログ・スタックトレース断片、またはそれへの添付リンク | フェンス内が設定・サンプルコードだけなら no。「ログなし」は no |
| steps | 初期状態や操作が少なくとも 1 つ具体的に示され、どう不具合へ至るか追える | 空見出し、テンプレートの説明、N/A、「時々起きる」だけなら no |

任意で `material_role` = input / action_sequence / observed_failure / expected_behavior / unknown を根拠ごとに記録する。
再現に十分か、添付が開けるか、著作権的に再配布できるかは、この yes 判定では保証しない。
不具合画面のスクリーンショットを、そのまま正しい期待画像にしない。

## 3. テスト関連の変更

変更ファイルのパス判定と、diff の内容判定を別に保存する。

**diff の向きに注意**：OSSGameBench の `diff` の patch は、通常と逆向き（子→親）に記録されている。
GitHub との照合で、向きを判定できた 70 件すべてが逆だった（[results/test_cases_final_v1](../results/test_cases_final_v1/README.md)）。
`-` の行が追加、`+` の行が削除。`change_type` も空。読むときは `scripts/13_check_patch_direction.py` の `invert_patch` で向きを戻す。

| 値 | 内容 |
|---|---|
| `executable_test` | テストとして実行される処理、チェック、アサーション等の追加・修正・削除。種別と操作を別記録 |
| `fixture` | 入力データ、期待画像、期待出力、リプレイ等。実行するテスト本体ではない |
| `infrastructure` | runner、CI、テスト設定等 |
| `documentation_manual` | 手動の確認手順、実行自動化のないサンプル、説明文 |
| `not_test` | テストに無関係。たまたま名前に test が含まれる等 |
| `unknown` | 内容を特定できない。バイナリ差分だけ、文脈不足等 |

RQ2 の最初の計測値は「候補パスの同時変更あり」とする。監査後に実行テストとの違いを報告する。
fixture だけの変更を executable_test と扱わず、同じ PR に両方ある場合は両方記録する。
diff から削除のみと分かる場合、「テスト追加」とは数えない。
テストの存在、対象バグの検出能力、CI での実行、成功、カバレッジの有無は別の概念。

## 4. 事例からテスト提案へ

1 例につき Issue、PR、commit、パスを残し、観察と提案を別々に書く。

- 観察：症状、報告にある材料、変更内容、観測されたテスト関連変更。
- 提案：初期条件、入力・操作、期待される結果、オラクル、実行条件。
- 追加で必要なもの：正常な期待画像、許容誤差、乱数の種、対応するゲームの版、ヘッドレス起動、テスト用の最小データ等。
- 限界：提案を実行していない場合、検出率や回帰防止の効果は未評価と明記する。

往復の保存テストでも、一時的な ID 等を除いた比較対象を定義する。状態の完全一致を無条件に要求しない。
ネットワークのハッシュ比較では、同期対象の決定的な状態と比較タイミングを定義する。全クライアントの内部状態が常に同じとは仮定しない。
クラッシュしないことは正しい挙動の必要条件の 1 つであり、一般的な十分条件ではない。
