# テスト戦略の提案 v1（2026-11-13）

Option B の「提案」部分。根拠にするのは、本分析（[results/rq_analysis_v1](rq_analysis_v1/README.md)）と、30 PR の内容分析（[results/test_cases_final_v1](test_cases_final_v1/README.md)）。
**どの戦略も実装・評価していない**ので、検出能力や効果は主張しない。観察（データ）、説明（推測）、提案を分けて書く。

## 提案の出発点（観察）

| 観察 | 数値 | 出典 |
|---|---|---|
| ゲームのバグ修正で、テストのファイルが変わるのは少ない | 6.2%（626 / 10,082） | RQ2 |
| 症状で差がある | ルール 8.6%、UI 4.5%、クラッシュ 4.1%、描画 3.7%、音声 0.8% | RQ2、GEE |
| テストを持つプロジェクトは限られる | 61 / 177 プロジェクト。fheroes2 は 1,262 件の修正で 0 件 | RQ2 |
| テスト変更ありでも、直接の回帰テストとは限らない | 30 件中 14 件 | 内容分析 |
| 実際の回帰テストは、状態や値を比べるものだった | 画像比較は 0 件 | 内容分析 |
| 報告には再現の材料が付いている | 画像 36%、対局リンク 10%（18xx では 65%）、セーブなどの添付 11%、ログ 8% | RQ1 の補助（規則は未検証） |
| 材料があってもテストになっていない | 18xx で対局リンクのある報告のテスト変更率 8.8%（リンクなし 14.6%） | 追加の集計 |

**提案の考え方**：報告に付いている材料を、テストの入力（初期状態と操作）に変える。正しさの判定（オラクル）は、画素ではなくゲームの状態で行う。
内容分析で実際に見つかった型を、テストのないプロジェクトや、材料はあるのに使われていない報告に広げる。

## 戦略 1：対局記録のリプレイによる回帰テスト

**対象**：ゲームのルール・状態のバグ（gameplay）。ターン制で、操作の記録を保存・共有できるゲーム（18xx、lichess、ボードゲーム・カードゲームの実装）。

**なぜ適しているか**
- 18xx では、報告の 65%（888 / 1,375）に、対局の記録へのリンクが付いている。多くは「action=404」のように**問題の手番まで**指していて、入力が報告の中にそろっている。
- 実際に、18xx#2558 では、報告された対局（game/17849）の記録をそのままテストデータにしていた。リプレイして、最終得点と「Game Over - Bankruptcy」の表示を確かめるテストだった。
- 決定的な（同じ入力から同じ結果になる）ゲームでは、乱数の種も記録に入っている（17849.json の `settings.seed`）。

**具体的なシナリオ**：18xx#7236（18EU。Minor Final Exchange Round で Pullman を捨てることが強制されない）
1. 入力：報告にある game/73766 の記録を、action=406（問題の直前）まで読み込む。
2. 操作：action 407 の時点で、RBSR が選べる行動の一覧を取得する。
3. オラクル：
   - (a) 選べる「捨てる」行動が、Pullman（P）だけである（報告者が書いた期待：「P を捨てることだけが選べるはず」）。
   - (b) 例外を出さずに最後までリプレイできる。
   - (c) 不変条件を満たす。株の総数は会社ごとに一定、銀行と全員の所持金の合計は保存される、列車の上限を超えない。

**正しさの判定の作り方**
- (b) と (c) は、どの対局にも使える汎用のオラクル。
- (a) は、報告の「期待される動作」の欄を、1 つのアサーションに書き直したもの。報告ごとに人が書く。

**実現可能性**
- 18xx はすでに、対局の記録をテストデータとして読む仕組みを持っている（`spec/fixtures`、`game_spec.rb`）。追加するのは、記録の取り込みと、途中の手番でのアサーションだけ。
- 報告に記録へのリンクがあるのは、18xx と lichess に偏る（リンク付き報告の 99%）。

**限界**
- ルールを修正すると、古い記録の結果も変わる。事例 9（18xx#2362）では、記録の更新と期待得点の書き換えが必要だった。期待値をどの版で固定するかの管理が要る。
- 記録にはプレイヤー名が入っている。テストデータとして公開してよいかの確認が要る。
- リアルタイムのゲームは、入力の時刻と物理演算の決定性がないと、同じ結果にならない。

## 戦略 2：「初期状態 → 操作 → 期待される状態」のシナリオテスト

**対象**：ゲームのルール、UI、クラッシュのバグ。報告に再現手順やスタックトレースがあるもの。

**なぜ適しているか**
- 直接の回帰テスト 14 件のうち、大半がこの形だった。
  - mage：カードを場に置く → 能力を起動する → ライフの値を確かめる。
  - space-station-14：椅子に座らせる → 致死ダメージを与える → 持ち物が落ちたか確かめる。
  - farmhand：作物が行の途中にある畑 → 検索 → 見つかるか確かめる。
- UI のバグも、画面の画像ではなく **UI の状態**（DOM の要素の有無）で判定していた（cuttle#378：ダイアログの後に `.v-overlay` が残らないこと）。
- クラッシュの報告の 31% にはログやスタックトレースがあり、失敗した関数が分かる。triplea#7292 では、そこから重複した座標を入力にした回帰テストを作っていた。

**具体的なシナリオ A**：fheroes2#2249（Berserker の呪文を受けた部隊が攻撃しない）。fheroes2 には、テストを伴う修正が 0 件。
1. 初期状態：報告の手順どおりの戦闘。Ruby・Luna の部隊、Cyclops、Red Dragons を配置する。
2. 操作：Cyclops に Berserker をかけ、Red Dragons の手番を飛ばす。
3. オラクル：Cyclops の手番で、隣接する部隊（敵味方を問わない）への攻撃が戦闘ログに記録される。または攻撃対象の部隊の HP が減る。

**具体的なシナリオ B**：ja2-stracciatella#2154（石を投げると segfault）
1. 初期状態：戦闘マップに、石を持った傭兵を置く。
2. 操作：投げる（物理演算を数ティック進める）。
3. オラクル：
   - (a) 異常終了しない。スタックトレースの `ExplosiveModel::getLightEffect` が null を受けない。
   - (b) 石が着地し、持ち物から消える（「落ちないこと」だけを正しさとはしない）。

**実現可能性**
- mage、space-station-14、18xx、lichess は、この形のテスト基盤をすでに持っている。
- fheroes2 や ja2-stracciatella に入れるには、描画なしで戦闘を進める仕組み（ヘッドレス実行）と、状態を作るための補助関数が必要。

**限界**
- 再現手順を状態と操作に書き直すのは、人の作業。報告の手順が曖昧なもの（例：「時々起きる」）には使えない。
- 「落ちない」だけのオラクルは弱い。必ず期待される状態も 1 つ書く。

## 戦略 3：古いセーブを読み込んで確かめるテスト（セーブの互換性テスト）

**対象**：セーブ・ロードと、ロード後のクラッシュ。ゲームの版が上がっても古いセーブを読めるか。

**なぜ適しているか**
- セーブなどの添付が、報告の 11% にある。クラッシュの報告では 18%、fheroes2 では 39%。
- 内容分析では、microcosm#175 が、古い形式の設定を読み込んで型と値を確かめるテストを強めていた（ロード後の終了時クラッシュの修正）。
- fheroes2#3775 のように、仕様変更で古いセーブが壊れる問題が報告されている。

**具体的なシナリオ**：fheroes2#3775（通行可否の変更で古いセーブが壊れた）と、報告に添付されたセーブ
1. 入力：Issue に添付されたセーブを集め、版ごとに並べたもの（例：fheroes2 の `Path.zip` などの添付）。
2. 操作：新しい版で、画面を出さずに読み込む。すぐに保存し、もう一度読み込む。
3. オラクル：
   - (a) 読み込みで例外が出ない。版の確認で、明示的に「非対応」と判定されたものは除く。
   - (b) 不変条件を満たす。英雄の位置が通行可能なマスにある、資源が 0 以上、所属の整合性。
   - (c) 保存 → 読み込みの往復で、一時的な ID などを除いた状態が一致する。

**実現可能性**
- 添付のリンク先は期限切れのことがある。集めたときに手元に保存しておく必要がある。
- 読み込みの関数を画面なしで呼べるかは、プロジェクトによる。

**限界**
- セーブの再配布には、報告者の許可と、セーブに含まれる元のゲームの素材の扱いの確認が要る。
- 「読めること」は、ロード後のゲームが正しく進むことまでは保証しない。

## 戦略 4：リアルタイムのゲームを、決まった時間だけ進めて状態を確かめるテスト

**対象**：連続的（リアルタイム）なゲームのルール・状態のバグ。結果では、テストを伴う修正が最も少ない側（3.3%。離散的なゲームは 8.8%）。

**なぜ適しているか**
- リアルタイムのゲームでも、テストを持つプロジェクトがデータにある。
  - **space-station-14**（修正 964 件中 46 件がテストを伴う）：画面のないサーバーを起動し、実体を配置して、ゲームの時間を決まった刻みだけ進め、状態を確かめる（内容分析で読んだ #1856、#28197）。
  - **omf2097/openomf**（格闘ゲーム）：操作の記録（`rectests/*.REC`）を再生するテストを持つ（[規則の検証](../validation/test_path_rule_v1/README.md)で見つけた。ファイル名からの判断で、中身は確認していない）。
- どちらも、「時間」と「入力」をテストの側で握ることで、非決定性を避けている。

**具体的なシナリオ**：space-station-14#1826（椅子に固定されたまま死ぬと、持ち物が落ちない）。実際に書かれたテストの形。
1. 初期状態：画面のないサーバーで、マップ、椅子、人間を作る。人間を椅子に固定し、手に物を持たせる。
2. 操作：致死量のダメージを与え、ゲームを数ティック進める。
3. オラクル：人間の状態が「死亡」になり、手が空で、持っていた物が床にある。

**実現可能性**：画面なしで起動でき、時間をテストから進められる設計が要る。乱数の種を固定する。入力の記録を再生できれば、戦略 1（リプレイ）と同じ形にできる。

**限界**
- 物理演算や浮動小数点の違いで、環境によって結果がずれることがある（許容する幅を決める必要がある）。
- 既存のゲームに後から入れるには、描画と処理の切り離しが必要で、手間が大きい（Murphy-Hill らの開発者が挙げた理由そのもの）。

## 戦略 5：音声と見た目を、音や画素ではなく「イベントと状態」で確かめるテスト

**対象**：音声と描画のバグ。結果では、テストを伴う修正が最も少ない症状（音声 0.8%、描画 3.7%）。

**なぜ適しているか**
- 内容分析で、実際の回帰テストは状態で判定していて、画像を比べるものは 0 件だった。UI のバグも、画面ではなく DOM の状態で判定していた（cuttle#378）。
- 不具合の画面のスクリーンショットは「正しい期待画像」にはならない。報告の画像（描画の報告の 55%）は、そのままではオラクルにできない。
- 音や画面の最終的な出力ではなく、その手前にある**再生要求のイベントや、シーンの状態**なら、コードで期待を書ける。

**具体的なシナリオ**：fheroes2#883（全体にかける呪文のとき、ドワーフの「呪文に抵抗した」音が鳴ってしまう。元のゲームでは、単体への呪文に抵抗したときだけ鳴る）
1. 初期状態：ドワーフの部隊を含む戦闘。音声の出力を、再生要求を記録するだけのものに差し替える。
2. 操作：全体にかける呪文（Mass Curse）を唱える。次に、単体への呪文を唱えて抵抗させる。
3. オラクル：全体の呪文の後には、抵抗の音の再生要求が 0 回。単体の呪文で抵抗した後には 1 回。

描画でも同じ考え方で、スプライトの向き、アニメーションのフレーム番号、描画の順序などの**シーンの状態**を確かめる。

**実現可能性**：音声の出力を差し替えられる作り（インターフェース）になっていれば、追加は小さい。

**限界**
- 再生要求が正しくても、実際に鳴る音が正しいとは限らない（音の途切れ、ミキサーの不具合は検出できない）。同じく、シーンの状態が正しくても、シェーダーやドライバによる見た目の不具合は検出できない。
- この 2 つの症状は、データにテストの実例がほとんどない。**裏付けは、UI のバグを状態で判定していた例からの類推**であり、5 つの戦略の中で最も根拠が弱い。

## 各戦略が検出できるもの：再発と、新しいバグ

課題は「バグの**検出**に役立つテスト戦略」を求めている。データで観察したのは、修正に伴うテスト（再発を検出する回帰テスト）なので、各戦略がどちらに効くかを分けておく。

| 戦略 | 報告されたバグの再発 | 未知のバグ |
|---|---|---|
| 1. リプレイ | 報告の期待を書いたアサーション | **不変条件**（株数・所持金の合計）を、集めた対局の記録すべてに流すことで検出しうる |
| 2. シナリオ | 期待される状態のアサーション | そのシナリオの範囲だけ（未知のバグには弱い） |
| 3. セーブの互換性 | 壊れたセーブの読み込み | 集めた**セーブすべて**を新しい版で読むことで、ほかの互換性の問題を検出しうる |
| 4. 時間を進めるテスト | 期待される状態 | 不変条件を入れれば、長く進めたときの異常を検出しうる |
| 5. イベントと状態 | 期待されるイベントの回数・順序 | そのシナリオの範囲だけ |

「検出しうる」は設計上の見込みで、実際の検出能力は評価していない。

## 離散的なゲームへの提案は、なぜ必要か

離散的なゲームは連続的なゲームよりテストを伴いやすいが、それでも修正の 91% はテストを伴わない。離散的なプロジェクトの 52%（73 件中 38 件）には、テストを伴う修正が 1 件もない（fheroes2 は 1,262 件で 0 件）。
戦略 1〜3 は、「再現と判定がしやすいはずなのに、テストされていない所」に向けたものである。戦略 4・5 は、「再現や判定が難しい所」に向けたものである。

| | 1. リプレイ | 2. シナリオ | 3. セーブの互換性 |
|---|---|---|---|

| 報告の材料 | 対局の記録（18xx は 65%） | 再現手順、スタックトレース | 添付されたセーブ（11%） |
