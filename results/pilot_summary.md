## #2 バグの特定

- ラベルは 4,273 種類。規則（`common.is_bug_label`：トークンに bug / defect / crash / regression などを含み、
  `not a bug` や `feature` などを含まない）で 123 種類をバグのラベルと判定した。
- 論文の「defect 58,900 件」は、ラベルがちょうど `bug`（大文字小文字を区別しない）の件数と一致する。
  表記の揺れをまとめると **84,356 件（26.4%）**。
- `duplicate`、`wontfix`、`invalid`、`stale`、`can't reproduce` など修正なしを示すラベル（93 種類）が付いたものを除くと、
  **分析対象は 81,620 件（701 プロジェクト）**。
- バグのラベルを一度も使わないプロジェクトが 242 件（Issue 42,924 件）ある。
- タイトルのキーワードは、バグのラベルが付いた Issue の 27.7% にしか当たらない（ラベルが非バグの Issue でも 6.8%）。
  **キーワードで補うのは難しい。ラベルのみで特定し、ラベルを使うプロジェクトに限られることを限界に書く。**
  規則の妥当性は、ラベルと Issue の手作業のサンプル確認で示す。

## #3 Issue → PR → コミットのリンク

- リンクされた PR があるバグ Issue：18,403 件（22.5%）。マージされた PR があるもの：17,497 件。
- `pr_commit` のコミットのうち、コミット表（本流の履歴）にあるのは 40.1% だけ。
  Squash や rebase でマージされた PR の元のコミットは履歴に残らないため。
- そこで経路を 3 つ用意した。

| 経路 | 方法 | 修正のファイルが分かるバグ Issue |
|---|---|---:|
| A | `pr_commit` のコミットが履歴にある | 7,020 |
| B | 履歴のコミットのメッセージが `(#PR番号)` または `Merge pull request #PR番号` | 13,592 |
| A または B | | **13,889** |
| C | コミットのメッセージに `fixes/closes/resolves #Issue番号`（PR を経由しない） | 14,074 |
| A、B、C のいずれか | | 24,851 |

- B で見つかる PR は、マージされたリンク PR 15,846 件のうち 79.6%（A と合わせて）。
- マージコミットにも変更ファイルが記録されている（ファイルが空の割合は 0.4%）。ただし、マージコミットの files が
  「PR 全体の変更」か「最初の親との差分」かは収集スクリプトで確認が必要。
- C は `#N` が別のリポジトリの番号を指す誤りがあり得る。使うならサンプルで確認する。

## #4 修正に含まれるアセット（A または B の 13,883 件）
