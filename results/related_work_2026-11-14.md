# 既存研究の調査：ゲームの種類・バグの種類とテスト（2026-11-14）

本人の問い：「ゲームの種類やバグの種類によって、テストの有無や方法が変わるのか」を調べ、適したテスト手法を提案し、テストがない理由も考察したい。既存研究で、すでに調べられているか。

調べ方：Web 検索と、主要な論文の本文の確認（Murphy-Hill ら、Pascarella ら は PDF の本文、Canella ら は arXiv の HTML の本文）。
その他は検索結果の要約だけで確認しているので、**引用する前に原典を読むこと**。

## 1. すでにある研究

| 研究 | 方法とデータ | テストについて分かっていること | 本研究との違い |
|---|---|---|---|
| Murphy-Hill, Zimmermann, Nagappan. *Cowboys, Ankle Sprains, and Keepers of Quality: How Is Video Game Development Different from Software Development?* ICSE 2014 | Microsoft の開発者へのインタビュー 14 人とアンケート 364 人（本文確認済み） | ゲームはテストの自動化が少なく、人がプレイして確かめる。**理由**：UI と処理を切り離しにくい、状態の空間が大きい、正しさを決めるのがデザイナーで主観的（「2 発で倒れる」をテストしても意味が薄い）、マルチスレッド・AI・乱数による非決定性、設計の変更で自動テストがすぐ古くなる、人のテスターが安い | 産業界の**認識**。リポジトリのデータで確かめていない。バグの種類やゲームの種類による違いは見ていない |
| Pascarella, Palomba, Di Penta, Bacchelli. *How Is Video Game Development Different from Software Development in Open Source?* MSR 2018 | OSS のゲーム 30 件とゲーム以外 30 件のリポジトリ、開発者アンケート（本文確認済み） | 調べたゲームにはテストケースがなかった。ゲームの開発者は自動の単体テストが難しいと答え、主に人が手で確かめている。今後の方向として record-replay（記録と再生）の道具を挙げている | **プロジェクト単位**の比較。個々の修正、バグの種類、ゲームの種類は見ていない |
| Canella, Duarte, Politowski, Durelli, Endo. *Characterizing Open-Source Video Games from a Software Engineering Perspective.* GAS '26（arXiv 2610.03953） | itch.io 由来の GitHub のゲーム 491 件（本文確認済み） | 自動テストがあるのは 36 件（7.33%）。テストの文書化も少ない。理由は推測（試作の速さと楽しさを優先） | **プロジェクト単位**。ジャンルとエンジンは集計しているが、**テストとの関係は見ていない**。バグ、修正、PR の分析はない |
| Politowski, Petrillo, Guéhéneuc. *A Survey of Video Game Testing.* AST 2021 / *Towards Automated Video Game Testing: Still a Long Way to Go* (arXiv 2202.12777) | 文献の調査、開発者アンケート（要約で確認） | 開発者はほぼ人の手によるプレイテストに頼る。自動のエージェントには懐疑的。手法がゲームの種類をまたいで使えるとは限らない | 実際のリポジトリでの計測ではない |
| Truelove, Almeida, Ahmed. *We'll Fix It in Post.* ICSE 2021 | Steam の人気ゲーム 30 本の更新ノートにある修正 12,122 件（要約で確認） | ゲームのバグの分類。情報のバグが最多、クラッシュは再発が多い | 更新ノートが対象。コードとテストは見ていない |
| Yu ら. *GameRTS: A Regression Testing Framework for Video Games.* ICSE 2023 | 商用ゲーム 1 本 | ゲーム向けの回帰テスト選択の手法 | 手法の提案。OSS の実態調査ではない |
| Chen ら. *GLIB: Towards Automated Test Oracle for Graphically-Rich Applications.* ESEC/FSE 2021 | NetEase のゲーム | 画面の不具合を判定するオラクル（画像の深層学習） | 描画のオラクルが研究課題であることの根拠 |
| ゲーム以外：Defects4J のバグ修正とテスト（arXiv 2310.19139） | Java のライブラリ | 修正のときにテストを追加・変更するのが一般的（追加 63% など） | ゲームではない。比較の相手として使える |

## 2. まだない（見つからなかった）もの

- **ゲームの種類（ターン制か、リアルタイムかなど）とテストの関係を、データで調べた研究**。Canella らはジャンルとテストの両方を集めているが、掛け合わせていない。
- **個々のバグ修正の単位で**、ゲームでテストが伴うかを測った研究。既存研究はプロジェクト単位（テストのフォルダがあるか）か、アンケート。
- **バグの症状ごとの違い**（音声・描画・UI・ルール）とテストの関係。
- Murphy-Hill らが挙げた**テストがない理由を、リポジトリのデータで確かめた研究**。

検索の範囲で見つからなかった、という意味で、存在しないことの証明ではない。

## 3. 本研究の位置付け（提案）

既存研究は「ゲームはテストが少ない」こと、そして開発者が考える理由を、アンケートとプロジェクト単位で示している。
本研究は、**バグ修正 1 万件の単位で、どの症状・どの種類のゲームでテストが伴うかを測り、開発者が挙げた理由と合うかをデータで確かめる**。

Murphy-Hill らの理由から、データで確かめられる予想を作れる。

| 開発者が挙げた理由 | データでの予想 | 今の結果 |
|---|---|---|
| UI と処理を切り離しにくい | UI のバグはテストを伴いにくい | **合う**（UI 4.5%、ルール 8.6%。オッズ比 0.68） |
| 正しさが主観的（デザイナーが決める） | 見た目・音のバグは最もテストを伴いにくい | **合う**（描画 3.7%、音声 0.8%） |
| 非決定性（乱数、スレッド、AI） | リアルタイムのゲームはターン制よりテストを伴いにくい | **向きは合う**（[RQ2b](game_type_v1/README.md)：修正の単位で 8.8% 対 3.3%。プロジェクトの単位では Web と規模を調整してもオッズ比 2.94。修正の単位は Web を調整すると不明瞭） |
| 設計の変更でテストが古くなる | テストの変更の多くは、既存テストの追従になる | 一部合う（内容分析 30 件中 10 件が追従だけ） |
| 人のテスターが安い | （データでは測れない） | 考察で触れるだけ |

- ここで「合う」は、予想と同じ向きの関連が観察された、という意味。理由そのもの（因果）を証明したわけではない。
- 「テストがない理由の考察」は、新しい理由を作るのではなく、**既存研究の理由をデータと照らし合わせる**形にすると、根拠のある考察になる。

## 4. 研究の組み立て（案）

- **RQ1**：バグの症状によって、修正にテストが伴う割合は違うか（実施済み）。
- **RQ2**：ゲームの種類（ターン制・決定的か、リアルタイムか）によって違うか（これから）。
  Web アプリかどうか、言語、規模を一緒に入れて、ゲームの種類の効果が残るかを見る。
- **RQ3**：テストを伴う修正では、どんなテストが書かれているか。入力をどう固定し、正しさを何で判定しているか（30 件で実施済み。ゲームの種類ごとに数件ずつ足すのも可）。
- **考察**：上の表で、開発者が挙げた理由とデータを照らし合わせる。
- **提案**：判定しやすさに応じたテスト手法（リプレイ、シナリオ、セーブの互換性。描画・音声は状態とイベントで判定）。
