## 判断

⑥（Option B）は継続する価値がある。ただし研究対象の呼び方を「テストの不足」から、
**「リンクされた修正で観測されるテスト関連ファイルの同時変更」**へ狭める。
テスト変更が見えないことだけでは、テスト不足も未テストも判定できない。
仮題も *Test Co-change and Reproduction Evidence in Open-Source Game Bug Reports* のように、観測できるものを前面に出す案がよい。
方針の最終確定は本人待ちとして残す。

提案を支えるために必要なのは、カテゴリ別の集計に加え、**同じバグ報告にある材料 → 再現操作 → 正しさの判定**がつながる実例である。
「画像の多い種類」と「テスト変更の少ない種類」が重なるだけでは、その画像をテストに使える証拠にはならない。
全 81,620 件の再現情報は背景の集計とし、テスト変更との組み合わせは修正にたどれる同じ対象に限定して示す。

## 予備調査コードから分かった測定上の問題

1. **カテゴリは現在、重複するキーワード一致。** 全文ではなくタイトル＋本文先頭 2,000 字を使い、`load`、`unit`、`sync` など広い語も含む。
   現在の種類別割合は、排他的なカテゴリの頻度ではない。計画中の「1 件 1 種類」と定義が違う。
2. **再現情報の有無と単なる言及が混在。** 「save file が壊れる」は添付ではなく、空の Steps 見出しも手順ではない。
   コードフェンスはコード例の場合もあり、画像ホストの URL は動画・ロゴの場合もある。未知の添付形式を画像へ割り当てない。
3. **テスト候補のパスは、テストの実行や追加の証拠ではない。** fixture、説明文、サンプル、手動確認用シーン等を区別する必要がある。
   変更ファイル一覧は追加・修正・削除を区別しないので、diff を見ない分析では「追加された」とは書かない。
4. **`code = 非テスト AND 非メディア` はコードを意味しない。** 設定・文書等も混ざる。
   したがって 35.6% 対 9.1% の後者を「コードだけ」と断定せず「core メディアなし」とする。アセットとテストの共起は fixture の影響を確認する。
5. **集計単位はバグ Issue。** 13,883 は変更パスが 1 つ以上観測できる Issue の数。1 PR が複数 Issue を閉じたり、1 Issue に複数 PR が付いたりする。
   修正イベント 13,883 件が独立に存在するとは言えない。対応表を保存し、PR 単位または最初の対象 PR に限る感度分析が必要。
6. **リンクと修正の関係も監査する。** マージ済みリンク PR と `(#N)` のメッセージがあっても、その全コミットが当該バグの修正とは限らない。
   `pr_commit` の経路とメッセージ補完の経路を分け、PR の本文・diff で補完例を確認する。メッセージ中の参照番号を無条件に修正番号とみなさない。
7. **履歴にテスト候補がある 695 プロジェクト**は、すべてのバグ修正時点でテストがあったという意味ではない。
   主分析の限定条件は「収録履歴で候補パスの変更が観測された」と表現し、実際のテスト保有率や当時の利用率とは呼ばない。
8. **13,889 と 13,883 の差は要照合。** pilot と探索で数が異なる。探索は `explode(files).dropna()` 後の Issue を数えるため、
   空のファイルリストが差の候補だが、この端末ではデータ未配置なので断定しない。両集合の差を出力してから確定する。

探索スクリプトと過去の出力はそのまま保存する。検証前に規則だけ変えて既存の数字と混ぜない。

## 相談事項 6 点への回答案

1. **筋道**：成立する。ただし同じ対象で再現情報とテスト変更を結び、少数の具体的な変換例で補強する。テストの不足や有効性の実証とはしない。
2. **分類**：主な症状は 1 つで集計してよいが、セーブ・ロードやネットワークは二次タグにもする。
   「ロードするとクラッシュ」をクラッシュだけにしてセーブの文脈を失わない。選べなければ複合・不明を認める。
3. **検証**：50 件の人との独立判定は授業の制約下での最低限の確認にはなるが、全カテゴリの高精度を保証しない。
   人の判定、LLM の判定、裁定後の参照判定を保存し、規則を調整する標本と評価する標本を分ける。
   同数の陽性・陰性標本やプロジェクト上限制限のある標本で、無補正の母集団精度を出さない。
4. **統計**：まず件数・分母・割合とプロジェクト別の分布を示す。全 Issue で重み付けした割合と、プロジェクトを等しく扱う集計を併記する。
   プロジェクト単位の再抽出で CI を付ける場合、各回で全 Issue を保持し、対象カテゴリがない回は無効として回数を報告する。
   単一プロジェクトにしかないカテゴリではその CI を根拠にプロジェクトを超えて一般化しない。回帰は必要な場合の追加分析とし、期限のために必須にしない。
5. **ゲームとツール**：混在は明記が必須。全 950 件を topics だけで二分するより、分析を支配するプロジェクトと事例対象から README で確認し、
   game / engine-tool / mixed / unknown を記録する。未確認を game にしない。確認済みゲームだけの結果は全ゲームの代表値とは呼ばない。
6. **削る部分**：RQ3 を 30〜50 の異なる PR の事例に絞り、回帰と 8 種類すべてへの提案を後回しにする。
   検証可能な 2〜3 種類に対し、具体的なシナリオ・オラクル・実行条件を提示することを優先する。

## 次に実データで確かめる順番

1. データ配置後、81,620 件の再現と 13,889/13,883 の差分を確認する。
2. Issue サンプルを作り、手引きを development で修正して固定する。人の独立判定 50 件を用意する。
3. テストパスの陽性・陰性を抽出し、実行テスト・fixture・非テストを監査する。
4. 補完リンク経路の正しさ、同一 PR の重複、game/tool 混在を確認してから本集計する。
5. 同じ対象で「再現材料あり・テスト同時変更なし」の実例を選び、具体的な提案へつなぐ。
