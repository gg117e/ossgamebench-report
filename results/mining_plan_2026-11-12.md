# バグ修正とテスト変更を中心にしたマイニング計画

2026-11-12。本人が「どの種類のバグ修正に、どんなテスト変更が伴うか」を中心に置く方向に同意。
以下は具体的な作業計画。データ準備・既存の探索再現は完了しているが、分類の最終検証と本分析は未実施。
従来の「テストの空白×全報告の再現情報」を同格に扱う計画から、修正単位の分析を中心に絞る。

## 中心の問いと成果物

中心の問い：ゲーム本体のバグの症状・発生文脈によって、リンクされた修正のテスト関連変更はどう違い、変更されたテストは何を入力・判定基準としているか。

- 主分析：種類別・プロジェクト別のテスト関連ファイルの同時変更率。
- 内容分析：30〜50の異なるPRについて、実行テスト、fixture、基盤、単なる保守等を区別し、ゲーム状態・入力・操作・期待結果を抽出する。
- 補助分析：同じ対象のバグ報告から再現材料を調べる。全81,620件の再現情報の詳細分析・回帰は必須にしない。
- 実践的な成果：2〜3種類のバグについて、実際のIssueを根拠に初期状態・操作・オラクル・実行条件を備えたテスト案を示す。

修正と一緒にファイルが変わったこと、当該バグに関連するテストが変わったこと、そのテストが実行・成功したことを分ける。
実行検証しないテスト案の検出能力や効果は主張しない。

## 1. 対象を決める

出発点は、従来の規則で抽出した81,620件のバグIssueのうち、マージ済みリンクPRから変更ファイルにたどれる13,883件。
これは検証済みの修正イベント13,883件という意味ではなく、現行リンク規則による候補集合である。

- プロジェクトのREADME・説明を確認して game / engine-tool / mixed / unknown を記録。主分析をゲーム本体に置き、ツールは別集計、不明は保留する。
- 分類後のゲーム本体の対象数と、除外による偏りを報告。950件全体や、すべてのOSSゲームを代表すると書かない。
- テスト候補が履歴にある／観測されないプロジェクトを分けて示す。履歴の候補変更だけで修正当時のテスト保有を認定しない。
- duplicate / invalid / wontfix等の除外規則は従来版を固定し、理由と件数を記録する。これらの除外後の母集団に限った結論とする。

## 2. 対応付けを監査可能な表にする

```
Issue → issue_pr → merged PR → pr_commit または squash/merge候補 → commit → 変更パス → diff
```

保持する表は、Issue、Issue–PR対応、PR–commit対応、commit–path対応を基本にする。
集計用のIssue表を別に作り、元の対応を消さない。

| 必須の記録 | 理由 |
|---|---|
| project、Issue番号、PR番号、SHA、パス | 原データへ戻れるようにする |
| 直接のpr_commit経路／メッセージ補完経路 | 補完リンクの誤りを監査できるようにする |
| PRの状態・日時、変更ファイル数 | 対象条件と時期・修正規模を確認する |
| 空のfiles、欠損、重複、複数PR・複数Issueの対応 | 分母と重複の影響を記録する |

13,889と13,883の差を実際のID集合で確認する。空のfilesが候補だが、未確認のまま原因を断定しない。
同一PRが複数Issueを閉じる場合は重複を識別し、主集計をIssue単位としても、PR単位・単一Issue対応のPRに限る感度分析を用意する。
単なる番号参照と修正の対応を区別し、経路別の無作為サンプルをPR本文・差分で監査する。

## 3. バグの症状を分類する

タイトルと本文の主症状を分類し、保存・読込、ネットワーク等の文脈は二次タグでも保持する。
例：「保存を読むとクラッシュ」は主症状crash_hang、文脈save_loadとして扱い、保存の情報を失わない。
ゲームのルール・描画・音声等について、既存分類に対応させた独自の操作的定義を固定する。

既存の `validation/samples-v1/` は**全81,620件からの標本**であり、狭めた主分析対象の最終評価用標本としてそのまま流用しない。
手引き試行の材料として保存し、ゲーム本体・リンクありの対象を確定後、その母集団から新しい評価用サンプルを抽出する。
既に読んだ事例は開発用に固定し、未使用の評価用標本に入れない。

- 規則の調整用と評価用を分離。想定は各100件、本人の独立判定50件は未使用の評価用側から選ぶ。
- 人とLLMの独立判定と裁定後の参照判定を区別する。分類者・実際のモデルID・根拠・手引き版を保存する。
- 自動分類は検証した規則を使用。不明を許し、カテゴリ別の精度・該当件数を報告する。
- 少数カテゴリの検証が不足する場合は追加監査、分類統合、記述的分析に限定する。LLMの自己確信度を精度の代わりにしない。

## 4. テスト候補の検出と内容確認を分ける

全対象の変更パスから `test/`、`*_test.*`、`*.spec.*` 等を候補検出する。陰性も監査して見落としを確認する。
陽性・陰性を同数抽出する場合は母集団の層の件数と抽出確率を保存し、全体の精度を無補正で合算しない。

内容分析では少なくとも次を分ける（1PRに複数付与可能）。

- 実行するテストの追加・変更・削除
- fixture・期待画像・期待出力・リプレイ等の変更
- runner・CI等の基盤変更
- モックや補助コードの保守、整理、当該バグとの関係が不明な変更
- 説明文、手動用サンプル、誤検出、判定不能

その上で、関連するテストについてバグの症状・操作・期待結果との対応根拠を記録する。
「回帰テストに関連する変更」は差分上の意味の対応として判定し、修正前に実際に失敗・修正後に成功したことを未実行のまま認定しない。
パスに基づく全体の率と、内容を監査したサンプルの結果を混同しない。

## 5. 集計と事例の選び方

まず全体と種類別に件数・分母・割合を示し、プロジェクト別分布も示す。割合は観測された同時変更率であり、テスト不足率ではない。
プロジェクト単位の再抽出で信頼区間を付け、少数プロジェクトだけのカテゴリは一般化を控える。
必要ならプロジェクトの差、時期、変更ファイル数を考慮する。回帰分析はデータ量と変動を確認した上で追加する。

感度分析は、ゲーム本体／ツール、直接リンク／補完込み、Issue／PR、テスト候補の定義、巨大プロジェクトの影響を中心に行う。

内容分析の30〜50PRは、テスト候補ありからプロジェクト・症状・変更規模を分散させて選ぶ。
多様性を優先した標本の割合を、そのまま全体の頻度として報告しない。テスト候補なしの事例も補助的に確認する。
各例で状態・入力・操作・オラクルを抽出し、報告にある材料が実際に使われたか、不明か、追加で必要かを区別する。

## 6. 新規性の現時点の評価

**有望な候補はあるが、修正時のテスト変更を調べること自体は既存研究にある。**
確認した文献の範囲での比較であり、網羅的レビューや「同じ研究が存在しない」という証明ではない。

| 近接研究 | 既に扱われている内容 | 今回との差を検討する場所 |
|---|---|---|
| [Lubsen et al., MSR 2009](https://pinzger.github.io/papers/Lubsen2009-coevolution.pdf) | 実装とテストの履歴上の同時変化 | 同時変更を数えるだけでは新規性にならない |
| [Sun et al., TOSEM 2023](https://yanmeng.github.io/papers/TOSEM231.pdf) | 同時変更だけでは意味のある共進化と限らないこと、識別方法 | パス候補と、対象バグに関連する内容を分ける設計が必要 |
| [Back to the Future!, arXiv:2310.19139v1](https://arxiv.org/html/2310.19139v1) | Defects4Jのバグ検出テストについて、報告後の追加・変更や変更内容を分析 | 「バグ修正とテストの中身を結び付ける研究はない」とは言えない。今回見たv1では掲載書誌の仮置きがあるので、引用前に最終版の書誌を確認 |
| [Truelove et al., ICSE 2021](https://arxiv.org/html/2103.03997v1) | ゲーム更新履歴のバグの種類・再発等 | 個々のPR・実際のテスト入力と判定をつなぐ分析との違い |
| [Canella et al., arXiv:2610.03953v1](https://arxiv.org/html/2610.03953v1) | ゲームのプロジェクト単位のテスト保有・実践 | 修正単位の症状・テスト変更内容・入力・オラクルとの違い |

貢献の候補は、ゲームの症状・状態に即して、どの入力や期待結果が実際のテストとして固定され、どこが候補パス変更だけにとどまるかを、修正単位で示すこと。
保存状態、描画、乱数、同期等のゲームの特徴が分析結果や判定方法に現れるかを確認する。違いが出ない可能性も含めて報告する。
分類手引きと、監査したIssue–PR–テストの対応を公開可能な形にすることは成果物として有用だが、公開するだけで研究上の新規性が保証されるわけではない。

課題レポートについてはOSSGameBench原論文の件数集計を超える分析を具体化できる。
MSRへの投稿に向けた新規性・十分性は、さらに近接研究を追い、得られた知見と分類・リンクの信頼性を見て判断する。

## 直近の実施順

1. 13,883件の監査可能な対応表と除外理由・経路を出力する。
2. 関連プロジェクトをgame/toolに分類し、ゲーム本体の分析対象数を確定する。
3. 主分析対象の新サンプルを作り、手引きと規則を検証する。既存の人用50件はまだ分類開始しない。
4. 全対象の候補パスを集計し、異なるPRの内容分析を行う。
5. 種類別の結果と、具体的なテスト案をまとめる。
