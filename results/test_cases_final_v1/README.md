# 最終差分のテスト変更の内容分析（30 PR）と diff の向き（2026-11-13）

CHECKPOINT の手順 6。v1 の 30 PR は全コミットの和集合から選んでいたので、最終差分（ランディングコミット）に基づいて選び直した。

## 1. 抽出（`scripts/09_extract_test_cases.py --final-dir`）

- 対象：game のプロジェクトで、Issue のすべてのマージ済み PR に最終差分があり、最終差分にテスト候補パスがある PR。
- 選び方は v1 と同じ（シード 20261112、1 プロジェクト 3 件まで、多様性のための標本）。旧評価標本（samples_game_v2）の audit の Issue を含む PR は除いた。
- 30 PR、18 プロジェクト、テスト候補のパッチ 55 個。取り出せなかったパッチは 0 個（v1 は 175 個中 10 個欠け）。
- 抽出の記録：[validation/test_cases_final_v1/extraction_manifest.json](../../validation/test_cases_final_v1/extraction_manifest.json)。

## 2. 重要な発見：データセットの diff は逆向き

読んでいくと、PR で**追加された**テストファイルが、全行削除（`@@ -1,65 +0,0 @@`）として記録されていた。GitHub のコミット API と照合した。

| 照合（`scripts/13*.py`） | 逆向き | 同じ向き | 判定不能* | GitHub になし |
|---|---:|---:|---:|---:|
| 30 PR のテスト候補パッチ 55 個 | 45 | 0 | 9 | 1 |
| 無作為な通常のコミット 28 個（15 プロジェクト、シード 20261113） | 25 | 0 | 2 | 1 |

\* 追加行と削除行の数が同じ（9 個）、または数が GitHub と一致しない（2 個）。

- 向きを判定できた 70 個は**すべて逆向き**（子→親）だった。`-` の行が実際の追加、`+` の行が実際の削除になっている。
  GitPython の `commit.diff(parent)` のように、親との差分を逆に取った可能性がある（推測。原因は確認していない）。
- `change_type` はすべて空。追加・削除のファイルは、パッチが全行 `-`（実際は追加）か全行 `+`（実際は削除）かで見分けるしかない。
- 影響：diff の行を使う分析（テストの追加と削除の区別、追加された行数など）は、向きを戻さないと逆の結論になる。
  変更ファイルの一覧（`files`）には影響しない。予備調査とテスト候補率は、パスだけを使っているので影響を受けない。
- 対処：`scripts/13_check_patch_direction.py` の `invert_patch` で向きを戻して読む。レポートの「データの限界」に書く。

## 4. テスト戦略の提案に向けて（観察から言えること）

- **対局記録のリプレイによる回帰テスト**（18xx）は、報告に操作の記録が付くゲームで、報告の材料をそのままテストの入力にできる例。オラクルは最終状態（点数など）と例外がないこと。
- **シナリオ型の状態テスト**（mage の `addCard` → `activateAbility` → `assertLife`）：初期状態・操作・期待される状態を、報告の再現手順に対応付けやすい。
- **セーブの移行テスト**（microcosm）：古い版のセーブを入力にして、読み込み後の型と値を確かめる。報告にセーブが添付されていれば入力にできる（今回の 30 件に添付セーブの利用例はない）。
- **画像比較の例は観察されなかった**。描画の不具合の提案は、データからの裏付けがない「提案」として区別して書く。

## 限界

- 30 件は多様性のための標本で、LLM による判定。人による検証、2 人目の判定者による一致度はない。
- パッチは 1 ファイル 45 行程度まで読み、長いものは必要な部分だけ検索して確認した。テストを実行してはいない。
- 「直接の回帰テスト」は内容から判断したもので、修正前に失敗し、修正後に成功することは確かめていない。
